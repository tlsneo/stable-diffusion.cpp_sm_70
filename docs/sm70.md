# NVIDIA V100 / SM70 构建与运行边界

本仓库使用配套的 SM70 ggml 子模块，面向 Tesla V100 / Compute Capability 7.0。请把源码版本、ggml 版本、编译选项和运行参数分别记录：相同的 `sd-cli` 文件名不代表相同能力，源码中存在后端实现也不代表本次二进制已经编译启用。

## 源码与依赖

首次获取时递归初始化子模块；已有工作区先审阅并保留自己的修改，不要用重置命令覆盖实验代码：

```sh
git clone --recurse-submodules https://github.com/tlsneo/stable-diffusion.cpp_sm_70.git
cd stable-diffusion.cpp_sm_70
git submodule status
```

默认使用当前 SD 提交固定的 `ggml/`，不自动切到独立 ggml 仓库的最新分支。ggml 的 CUDA 子模块包含固定的 CUTLASS 来源，不需要另一项目的本机 `.deps` 路径。若改用 `SD_GGML_SOURCE_DIR`，须显式记录并验证外部 ggml 的提交与子模块。

不要把模型权重、生成媒体、提示词、运行日志、凭据或机器绝对路径加入源码仓库。

## 已使用的构建组合

下面保留 Krea2 / Qwen-Image 2.1 图片与 MiniMax-H3 既有构建的选项差异，不把实验目录或旧 `CMakeCache.txt` 当成发布入口。构建需要兼容的 CUDA 工具链与 C++17 编译器；V100 既有验证使用 CUDA 12.4。

| 选项 | 图片构建 | H3 构建 |
| --- | --- | --- |
| `CMAKE_CUDA_ARCHITECTURES` | `70` | `70` |
| `SD_CUDA` | `ON` | `ON` |
| `GGML_CUDA_CUTLASS_SM70_ATTN` | `ON` | `ON` |
| `GGML_CUDA_FLASHINFER_SM70_ATTN` | `ON` | `ON` |
| `GGML_CUDA_GRAPHS` | `OFF` | `OFF` |
| `GGML_CUDA_TURBOMIND_SM70` | `ON` | `OFF` |

TurboMind 的差异用于复现既有二进制选项，不表示 H3 永远不能使用 NVFP4。已保留的 H3 实机结果使用 INT8 ConvRot，不能将其当作 H3 NVFP4 端到端验收。

### Krea2 / Qwen-Image 2.1

```sh
cmake -S . -B build-sm70-images \
  -DCMAKE_BUILD_TYPE=Release \
  -DSD_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=70 \
  -DGGML_CUDA_CUTLASS_SM70_ATTN=ON \
  -DGGML_CUDA_FLASHINFER_SM70_ATTN=ON \
  -DGGML_CUDA_TURBOMIND_SM70=ON \
  -DGGML_CUDA_GRAPHS=OFF \
  -DSD_SERVER_BUILD_FRONTEND=OFF
cmake --build build-sm70-images --target sd-cli -j 8
```

### MiniMax-H3

```sh
cmake -S . -B build-sm70-h3 \
  -DCMAKE_BUILD_TYPE=Release \
  -DSD_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=70 \
  -DGGML_CUDA_CUTLASS_SM70_ATTN=ON \
  -DGGML_CUDA_FLASHINFER_SM70_ATTN=ON \
  -DGGML_CUDA_TURBOMIND_SM70=OFF \
  -DGGML_CUDA_GRAPHS=OFF \
  -DSD_SERVER_BUILD_FRONTEND=OFF
cmake --build build-sm70-h3 --target sd-cli -j 8
```

并发数应按主机内存调整；两组使用不同构建目录，避免缓存选项串用。若旧缓存仍指定外部 CUTLASS，优先使用新的构建目录，不直接覆盖旧验证产物。

## Attention 与 Graph 路由

既有运行显式设置：

```sh
export GGML_CUDA_DISABLE_GRAPHS=1
export GGML_CUDA_SM70_ATTN=auto
```

`auto` 只在本次已编译后端及其支持的 dtype、形状条件内选择，不会把未编译的 CUTLASS / FlashInfer 自动补出来。显式请求后仍须核对实际路由，不能把回退路径记录为 CUTLASS / FlashInfer 已经运行。

运行设备由调用方通过 `CUDA_VISIBLE_DEVICES` 和 `--backend` 等参数显式选择；本文不固定 GPU UUID、GPU 序号、模型路径或 NUMA 节点。也不要把某次显存预算、seed、尺寸或参考数量写成通用默认值。

## 多 GPU 连续层分配

图切分的 `layer` 路径优先按各后端可用容量规划接近均衡的连续层边界，避免先填满第一张卡。均衡目标因不可拆分层而规划失败时，回退原来的连续容量优先策略，避免拒绝原本可容纳的布局；不承诺全局最优装箱。可复用的既有参数分配保持原路径。

容量规划不能替代真实运行图与临时工作空间检查。权重放得下，不等于采样峰值也放得下；多卡容量总和也不能证明每张卡的峰值安全。

## H3 条件与验证范围

详见 [MiniMax-H3](minimax_h3.md)。普通参考图、首尾 Guide、视频／音频接力是不同条件，不应只因接口接受参数就宣称真实成片全部通过。

- 既有 V100 记录包含纯 Ref2VA、连续层分配、1024×576、24 fps、20 步、73／124 帧及不同普通参考图组合的实际结果；这不是任意参数组合的能力保证。
- 普通参考与首尾 Guide 混用的迁移包含布局支持；CPU 布局断言不能代替真实 Guide 成片、跨段一致性或声音内容验收。
- 连续尾帧音画接力、额外 LoRA、二采、增强或隐式转码不因本次迁移而自动启用。
- 本次正式源码迁移的 CPU 构建／布局检查与此前 GPU 成功记录分开记账；没有重新运行完整模型，不把新构建选项的源码合并等同于新二进制已经通过 GPU 回归。

正式使用新的 GPU 构建时，应在独立输出目录核对模型身份、输入顺序、尺寸、帧数、实际媒体格式／音轨与子进程状态，保留已有可用程序和必要的私密诊断。生成失败不自动降参数或重跑。
